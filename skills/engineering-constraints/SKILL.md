# Engineering Constraints · 工程决策约束

## 适用
当用户要求设计架构、做技术方案、迁移/重构、选型、评审、代码修改或交付时先应用本 Skill。若仅问常识，不增加多余流程。

## 输入与事实
1. 识别当前项目、分支、版本、设备、现场条件、交付对象。不同仓库/项目视为隔离；没有授权不得交叉复制源码、协议、数据或客户信息。
2. 建立三栏事实表：已验证事实 / 合理假设 / 待现场或文档确认。引用仓库文件路径及提交号；无法访问时明确声明，绝不编造“已核实”。
3. 识别不可变化约束（硬件结构、接口时序、兼容版本、人员权限、验收指标）和可协商选项。
4. 只问阻断实施的关键信息；能合理推进时先采用显式、保守的假设。

## 决策流程
1. 先写目标、非目标及成功指标。
2. 至少比较保留现状、最小改动和完整方案；说明复杂度、维护成本、风险、迁移与回退。
3. 影响真实设备时优先评估联锁、故障失效模式、手动/自动冲突、断线、超时、急停及恢复；不可用软件说明替代电气/机械安全设计。
4. 可逆性优先；先验证关键假设或做最小冒烟，再做不可逆变更。
5. 明确谁审批、谁执行、如何验收，确保状态和证据可追踪。

## 执行合同
- 修改代码前：列出影响文件、接口/ABI变化、兼容性和验证计划。
- 修改代码后：列出改动摘要、实测命令及结果、未验证项、风险和回滚方法。
- 判断与数据分离：算法判定 OK/NG/NoResult 不等于设备故障/停机状态；错误不可静默吞掉。
- 文档、汇报、宣传应标注数据来源、日期和版本；不得捏造测量精度、良率、速度、收益及验收结论。

## 交付格式
目标与边界 → 事实/假设 → 方案与取舍 → 失效模式 → 验证矩阵 → 决策记录（日期、责任人、待确认）。
